## Follow-up: Desktop scroll-follow triage

User reports that workflow output does not automatically follow the bottom.
Expected UX: follow new output and phase continuations when already pinned to
the bottom; preserve position after intentional upward scrolling; allow an
explicit jump-to-latest to re-enable following.

Read-only triage: the Arbiter ends a native turn and starts the next phase
internally, rather than through the Desktop Send action. A client-side follow
reset at that boundary is a hypothesis, not a reproduced root cause. The
presentation layer preserves native turn start/completion events. Current
handoff/presentation regressions pass 32 with one opt-in skip; these protocol
tests do not prove visible scrolling. Neither the installed generated App
Server schema nor the official App Server reference exposes a scroll field.
No production code, UI workaround, deployment or app restart was performed.

Pending native async question, scoped to Desktop scroll-follow acceptance:
if the user manually returns to the bottom during a workflow, does following
resume until the next phase change, remain stopped, or is the behavior unknown?
Live reproduction and the UI-versus-handoff fix decision remain parked until
that observation is available. Do not interpret silence as an answer. Compare
an ordinary streamed turn with a workflow continuation, both bottom-pinned and
intentionally scrolled up, before changing protocol behavior. Telemetry live
