# Claude and Codex host release compatibility

## Current incident and evidence

On November 12, 2026, a user reported that Statewright 0.3.8 at public source
`921dc4881c1b861b6d00c45e769d30890f928f8b` could sign in through the native Claude
CLI, but Claude Desktop Code engine `2.1.321` continued reporting `auth`.
The external CLI was `2.1.323`, updated from `2.1.282`. Desktop rejected
`/mcp reconnect plugin:statewright:statewright` with:

> Reconnect, enable, and disable aren't available in this session.

This is a reported runtime failure, not a newly executed reproduction. The
Desktop app version/build, embedded binary identity, plugin artifact digest,
OS version, actual `command.run` return/exception and last working host build
are missing. A recent Desktop update is a hypothesis, not an established
regression boundary. A healthy gateway and a connected CLI do not prove that
the live Desktop session imported the credential.

The follow-up report identifies the primary failure in Desktop's
`verifyPluginMcpBinding`: it compares the raw `${user_config.gateway_url}`
placeholder with the engine's resolved gateway. The reported log is
`URL mismatch; expected=<unparseable> resolved=https://mcp.statewright.ai`.
The user replaced the placeholder with the literal production MCP URL in both
the installed cache and marketplace checkout, then fully restarted Desktop and
confirmed sign-in worked. That is reported recovery evidence for the local
manifest patch, not acceptance of this combined candidate or every host check.

This candidate ships a literal URL, removes the now-unused gateway preference,
and directs Desktop Connect through the host's `/mcp` dialog. Custom gateways
must use a separately prepared package with a literal endpoint; existing
custom-gateway users must prepare that package before upgrading. Desktop never
uses the external CLI helper. Terminal startup/sidebar checks can reload saved
credentials once before offering OAuth; a waiting tool hook cannot run slash
commands, so its quiet check does not attempt reconnect. Terminal reload
refusals remain visible and a completed helper is not run again in that view.
The plugin never reads the credential store itself. External-CLI-only import
after restart has not been separately verified.

The official [mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
points to the [types generated by the actual host build](https://code.claude.com/docs/en/plugins/mods/create#get-type-definitions-for-your-version)
as authoritative. The public declarations checked here describe `command.run`
as returning optional `text`; they do not establish a credential-refresh option
for this installed engine. Do not invent one. Tests cover the reported refusal
as returned text and as an exception; neither is claimed as a captured API result.

## Separate acceptance lanes

Maintain four lanes: **Claude CLI, Claude Desktop Code Local, Codex CLI, Codex
Desktop**. A CLI pass never qualifies its Desktop lane. A Desktop app version
never substitutes for the engine version bundled inside it.

The append-only [ledger](host-compatibility.json) records exact combinations:

- Desktop application version and build; use `not-applicable` only for CLI lanes.
- Actual session engine version and build identity (binary SHA-256 if no build
  ID is exposed). Record the running engine, not a different executable on PATH.
- External CLI version, OS version and architecture.
- Statewright plugin version, exact source SHA and installed artifact SHA-256.
- Gateway origin. Never include OAuth callbacks, tokens, keys or account data.

On any change to those values, append an **untested** record. Retain the last
working receipt. A changed binary under the same version is a new boundary.
Do not mark an unknown identity as passing or carry a previous pass forward.
Records are appended in observation order; a later failure for the same tuple
supersedes its earlier pass. Keep separate receipt artifacts for each lane.

## Required acceptance at a host boundary

For the same plugin artifact and gateway, compare the last working host with
the updated host in an isolated test profile when available. Do not downgrade
or restart a user's active host automatically. If the earlier build is
unavailable, record the first observed failure; do not call it the first broken
release.

Each passing record needs a timestamp and evidence for all nine scenarios:

| Check | Required observation |
| --- | --- |
| `freshLogin` | Browser approval reaches the same live session; native server identity and catalog verified. |
| `externalLoginReload` | Login outside the host becomes visible without another OAuth loop; record exact reload API outcome. |
| `expiredCredentialRecovery` | Renewal restores the waiting session without duplicating the blocked action. |
| `catalog` | Actual authenticated catalog arrives; an empty UI is not interpreted as success. |
| `permissionDenial` | Native denial remains denied; no alternate transport, login or automatic retry bypass. |
| `workflowApproval` | Approval reaches the right disposable run/conversation once; no cross-session approval. |
| `modelRouting` | Observed request/response uses the intended route; selected-model UI alone is insufficient. |
| `cancelAndResume` | Cancelled or late work cannot alter another conversation; history remains valid. |
| `restartAndResume` | Cold start and resume recover the expected connection/run, with exact host identity recorded again. |

These live cases require the ordinary authorization for sign-in, disposable
workflow actions and host restarts. This document does not authorize them.
Mock tests, a transport HTTP 200 and CLI `Connected` are supporting evidence,
not replacements for interactive acceptance.

## Local validation and exact candidate check

Validate the ledger and its checker without starting any host:

```sh
node --test scripts/host-compatibility.test.mjs
node scripts/host-compatibility.mjs docs/releases/host-compatibility.json
```

Create a candidate identity JSON with all fields listed in a ledger `identity`
object, filled from the actual candidate. Then require a matching accepted row:

```sh
node scripts/host-compatibility.mjs docs/releases/host-compatibility.json \
  --require-accepted /absolute/path/to/candidate-host-identity.json
```

Missing identities, changed versions/builds/artifacts, absent scenario evidence
and a superseding failure all fail this check. The initial ledger deliberately
contains **no passing records**. The checker validates receipt completeness and
identity matching; a reviewer must verify the referenced evidence itself.

Existing `plugin-version-canary.yml` tests source or release artifacts and
transport/adoption behavior. It explicitly excludes authenticated interactive
vendor-host acceptance. Codex vendor canaries in `plugins/executor/tests/`
provide narrower receipts for routes, approvals and resume; record their exact
executed commands, binary identities and results alongside the live UI cases.
Do not treat a skipped opt-in canary as a pass.

The ledger/checker tests run in `task test:plugin-release`, already used by the
plugin contract CI job. They check record integrity; they do not turn untested
hosts into accepted hosts. The exact-candidate acceptance command above remains
a separate local check. No scheduled release watcher, host installation or
compatibility publication is added here. Requiring live receipts in release
promotion and running interactive host acceptance remain follow-up release work.
