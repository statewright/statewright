## The Thesis

> **Agents are suggestions. States are laws.**

The model can rationalize away instructions.

It can't rationalize away a blocked tool call.

Note: This is the one-liner. A state machine doesn't negotiate with the model. It doesn't care how confident the model is. If Edit isn't in the allowed tools for this phase, the call gets rejected. Period.

---

## What a Workflow Looks Like

```json
{
  "planning": {
    "allowed_tools": ["Read", "Grep"],
    "max_iterations": 5
  },
  "implementing": {
    "allowed_tools": ["Read", "Edit"],
    "max_iterations": 8
  },
  "testing": {
    "allowed_tools": ["Read", "Bash"],
    "allowed_commands": ["*test*"]
  }
}
```

Note: Three phases. Planning is read-only — the model literally cannot edit. Implementation unlocks Edit. Testing restricts Bash to test commands only. Each phase has an iteration budget. This is the entire enforcement layer — it's a data structure, not a prompt.

---

## When the Model Disobeys

```
⏺ Edit(src/main.py)
  ⎿ PreToolUse hook (blocked)

  Tool 'Edit' not available in 'planning'.
  Allowed: Read, Grep, Glob.
  Transition with: READY → implementing.
```

The model sees this. It adjusts.

Note: The hook blocked it, told it exactly what IS available, and how to advance. The model doesn't spiral — it gets concrete feedback. This is enforcement, not a suggestion.

## Why Smaller Models Work

The model doesn't get 30 tool definitions.

It gets 3.

```
Planning:  3 tools   (~1,400 tokens)
Full set:  30 tools  (~10,500 tokens)
```

On a 16K model, 30 tools eat **64%** of context.

Per-state scoping: **3x more room for code.**

Note: This is the technical reason retry nudges aren't sufficient. You can retry all day — if 64% of context is tool definitions, reasoning quality is the bottleneck. Smaller tool space = better reasoning.

---

## The 9B Self-Correction

A 9B model tried a complex tool 3 times.

Failed each time. Auto-test caught it.

Bounced back to implementing.

**4th cycle: switched to a simpler tool.**

One call. One line. All tests green.

Note: gemma4:e2b, 7.2GB on a single GPU. Couldn't serialize JSON for patch_file — capability limitation at 9B. But the retry loop gave it enough attempts to discover edit_line, a simpler tool. The guardrails provided the safety net. The model provided the adaptation.

## Per-State Model Routing

Not every phase needs a frontier model.

```
planning:      gemma4:12b  (local)
implementing:  llama3.3    (local)
testing:       gemma4:12b  (local)
critical call: Opus        ($0.10)
```

**79% cost reduction. Same results.**

Note: Pi's extension API supports setModel(). Claude Code can't do this. Codex can't do this. The cheap model handles 18 of 20 steps. The frontier model fires once for the one decision that matters.

## Auditability

Every transition is logged with rationale.

```
planning → implementing
  "Bug in converter.py:11"
implementing → testing
  "Fixed formula: 9/5 → 5/9"
testing → implementing
  "test_roundtrip still failing"
testing → completed
  "All 6 tests green"
```

Not observability. A **decision trace.**

Note: If someone asks "why did the agent change this file?" — the answer is in the transition log. Each transition carries a rationale. Each phase has constrained tools. You can reconstruct what the agent could and couldn't do at every point.

## Demo: Planning Phase

Read-only. The model can't edit yet.

Note: Point out — planning only has read tools. The model reads, greps, understands the codebase. Then it transitions. No premature editing.

## Demo: Implement + Test

```
[sw] Phase: implementing. Tools: read, edit.

⏺ edit(src/converter.py, ...)
  9/5 → 5/9

[sw] Transition: DONE → testing

⏺ bash(pytest tests/ -v)
  6 passed ✓

[sw] Transition: TESTS_PASS → completed
```

Note: Implementation unlocks edit. One targeted fix. Testing runs pytest — restricted to test commands only via allowed_commands. Clean progression through phases.

## What You Can Take Home

1. **Per-state tool restriction**
2. **Iteration budgets**
3. **Programmatic states** for mechanical work
4. **Transition guards** in code, not prompts
5. **The tool interface matters**

Note: These patterns work regardless of framework. You can implement this in Claude Code hooks, a Python wrapper, a bash script. The point: structural enforcement beats prompt engineering.
